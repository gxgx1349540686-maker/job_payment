## 技术实现

使用自编顺序状态机：接收→解析→匹配→规则→编排SQL→校验只读执行→汇总→SSE输出。运行入口`app.py`使用`agent/engine.py`，不再依赖LangGraph编排或LangChain模型适配。难以提取对象时通过`agent/provider.py`的HTTPX直接调用DeepSeek，0自动重试；明确需求可完全走本地解析，避免为生成固定SQL额外调用模型。

FastAPI、Uvicorn、原生网页、SQLGlot、RapidFuzz、HTTPX、SQLite及Python整数分计算继续使用。锁定依赖已按实际安装的依赖闭包重新生成；旧LangGraph代码保留作历史参考，不参与新版运行。

## 匹配与澄清

- 优先识别用户明确提供的项目、楼栋、合同ID/完整名称、单据号。
- 完全匹配且唯一的实体直接采用；模糊候选严格超过90分且唯一时自动采用。
- 需要选择时，存在超过90分的候选只展示这些候选；否则展示前5个。
- 超过90分仍有多个且没有唯一完全匹配时，必须选择，不能擅自取最高分。
- 名称匹配分数是本地字符串相似度，不是模型准确率概率。数字楼栋不高分匹配到不同号码；年份和月份不能被误当楼栋编号。
- 模型补充提取的名称若未在原输入中出现，不允许直接自动采用，候选分数上限90并请求确认。
- “应收”没有我方/业主费用等依据时先选口径；清晰的收入、应付、实付及差额不重复询问。
- 每次结果都明确列出实际采用的对象、范围、账期和版本。

## 功能

| 入口 | 输出 |
|---|---|
| 项目 | 项目月度和总额、执行合同、相关楼栋；可要求各楼栋明细 |
| 楼栋 | 每月实收、应收业主费用、应付、成功实付及差额 |
| 合同ID/名称 | 相关楼栋、执行月份、付款和费用；无法唯一归属的月金额只列楼栋参考额 |
| 实付单据号 | 单据原金额、状态、来源月份；本单据与整月成功实付分开，分别比较当月应付 |

默认不限制月份，查询全部已存日期；单据查询未提供账期时采用该单据来源月份，明确说明。按实际付款日期、具体日和相对日期尚不支持，会要求明确账期。

账面应付差额=同范围同月份应付－成功实付；实收差额=实收－应付。单据差额=当月应付－本单据成功金额，不能替代整月差额。均不代表已核销余额或已确认欠款。

## 关联与重复累计约束

执行合同通过T08_执行合同展示单独查询，不联表展开金额。合同金额只有在月度记录的唯一执行合同等于所查合同且应付已知时才可以归属；否则合同金额和差额为空，另列楼栋参考额。合同多楼栋且未分摊的成功付款不能强行拆到单栋；当项目包含整份合同的楼栋时，项目合计可以按单据号计一次。分楼栋表和项目合计的付款归属可能不同，不能把分楼栋待分摊金额再次累加到项目合计。

R35已经确认无科目发生记录时月度采用0，但资料完整性仍不保证；源空值、缺楼栋ID及未知应付保持未知。没有月度查询记录不能认定0元。负数不截断。

## 流式页面与SQL

通过POST `/api/chat/stream`持续输出任务摘要、名称匹配依据、采用口径、SQL编排片段、参数预览、校验执行结果、答复和表格。SQL是服务端根据审核计划编排的参数化SELECT，用户输入只作为绑定参数，不拼接SQL。

前端“任务解析与SQL编写过程”默认展开，能看到本次真实查询过程；最终还可展开“实际执行SQL及全部绑定参数”。这不是模型私有思维链，也不是把未校验模型Token当作财务结论。

## 提示词与向量数据库是否需要

需要编写提示词：已新增`knowledge/r35_prompts.json`，只让模型补充提取实体，禁止生成金融结论、猜合同或提供虚构置信度。

独立向量数据库不是必需条件：本项目规则只有9条，可直接按指标加载。为了沿用现有规则维护和来源检索，当前仍生成轻量`runtime/r35_rules.sqlite`字符TF-IDF向量库；关键规则强制加载。没有引入付费Embedding、Chroma或Qdrant。随着规则增长可以替换检索实现，但不能让检索代替强制财务规则。
